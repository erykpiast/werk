## What to build

`werk run <subtree-id>` is the person's start of a run over that subtree's tickets; running it again resumes. Its first event in the board log is the tier, always feature, since v0 has no way to say or raise a tier, and every gate it reaches waits for a person. A run started event names the merge-loop process; a run ended event closes it.

The loop builds ready tickets whose blockers are merged (one at a time in this ticket), then takes each finished ticket through a merge queue one at a time: it merges the ticket's branch onto the main line's tip in a detached temporary worktree and runs the ticket's checks there. Red checks merge nothing and send the ticket back to building with the failure; the next build starts from the old branch when it sits on top of the main line. Green moves the main line only from the value it had when the merge started; a checkout of the main line moves with it by fast-forward, and local changes that block the fast-forward stop the loop with nothing moved. The ticket goes to done.

A ticket at its retry cap moves to blocked with the reason, with every ticket that needs it, and the loop goes on with the others; the run ends only when nothing can build or merge, and reports each stuck ticket and what waits on it. A loop that stops for any reason moves every ticket it left in building or merging back to ready with the stop reason. G2 belongs to the main line's tip and opens when every ticket of the subtree is merged.

## Acceptance criteria

- [ ] A run over two independent tickets builds both and leaves two merge commits on the main line.
- [ ] The first board event of every run is the feature tier.
- [ ] A ticket that passes alone but fails its checks on the merged tree goes back to building and does not merge.
- [ ] A stuck ticket blocks its dependents only; an unrelated ticket still merges.
- [ ] A stopped loop leaves no ticket in building or merging.
- [ ] A main line moved by someone else during the merge checks is not overwritten.
