Ready3
Render 5 columns with counts

Lay out the five fixed columns — blocked, ready, building, merging, done — as a single horizontal board. Each column header shows the column name and a live count of the tickets currently inside it, updated whenever a ticket moves in or out.

Column identity and order are fixed in code, per #werk-board-columns: blocked, ready, building, merging, done, always in that order, never reordered by a person and never configurable per run. Only which tickets sit inside a column changes at runtime; the columns themselves are not a piece of state anyone edits.

Each column needs its own scroll region once it holds more tickets than fit on screen, so a long-running build with many tickets in ready does not push the other columns off screen. The header and count stay pinned while the ticket list beneath it scrolls.

This ticket only lays out the shell: five columns, headers, counts, and a scrollable body per column. It does not implement drag-and-drop, the trigger or archive actions, or the ticket detail drawer — those are separate tickets — so this slice can be shown working with static placeholder tickets before any interaction exists.

Wire reorder + archive + trigger + stop actions

Implement the four direct actions #werk-board-control decided: reorder a ticket within ready by dragging it, archive a ticket (ready or blocked only), trigger the build of a ready ticket, and stop the build of a building ticket by dragging it back to ready.

The drag surface is column-aware: dragging within ready reorders; dragging a ready ticket into building shows a green "start the build" drop area and triggers the same effect as the trigger icon; dragging a building ticket into ready shows a red "stop the build" area. Every other column pair refuses the drop outright — no overlay, no drop, the cursor shows not-allowed — because those moves are not a person's call: ready/blocked changes only through an agent, and building/merging/done only through the merge loop.

Archive asks for confirmation before it does anything, and the confirmation text says plainly that the ticket is not deleted for good — an agent can restore it. This mirrors #werk-remove, the same reversible pattern already decided for a map card, so a person does not have to learn two different mental models for "this is gone but not really gone."

No ticket starts to build on its own in this ticket's scope. Every build begins with an explicit trigger, whether that is a click or a drag; only later, if every new ticket turns out to need a build anyway, does the trigger go away and builds start themselves.

Follow-up: fix held-out regression

Filed automatically, not by a person: the held-out set went red on the step "graph view loads a 200-card map" after the last merge to the run's tree. Per #st-g2-heldout, a red held-out step does not block the merge queue and does not stop the run — it only opens a follow-up ticket and keeps G2 from closing.

The regression traces to a change in src/fold.ts's rollup counting: a card with more than 200 descendants now takes a slow path that the graph view's render loop was not budgeted for. The fix is either to cache the rollup or to raise the render loop's frame budget for large graphs; the ticket does not prescribe which, since that is an implementation call for whoever picks it up.

Once this ticket's fix merges, the held-out set re-runs on the new merged tree automatically — nobody has to manually re-trigger the check. If it is green, G2 stays open; if it still fails, another follow-up ticket is filed the same way, and this one closes with a note pointing at the new ticket.

This ticket carries real cost if it sits too long: the run's tree is currently red on this one held-out step, which is an accepted cost per #st-g2-heldout ("the run's tree can be red on a held-out step until the follow-up ticket is built"), but it means every person looking at the board sees a stale-looking status until this merges.

Merging1
Ticket card shows cited ids + blockers

A ticket's full detail view lists the map ids it cites and what blocks it, read straight from the ticket file's own cites and blocked_by fields (#st-ticket) — there is no separate data model or cache to keep in sync with the ticket file on disk.

blocked_by is derived, not guessed: it comes from the depends_on edges between the cards a ticket cites, so if ticket A cites a card that depends_on a card ticket B cites, A is blocked_by B automatically, and the planner is responsible for computing that graph correctly before any ticket reaches the board.

This ticket only renders what is already computed; it does not implement the derivation itself, and it does not validate that the blocked_by graph is acyclic or agrees with depends_on — those are checks #lp-checks already owns, run once by the planner, not re-run by the board on every page load.

The checks are running now on the temporary tree made from the run's tree plus this ticket (#st-build-run, steps 1–2): if they come back red, this ticket goes back to building with the failure attached; if green, it merges into the run's tree and the held-out set gets one more ticket's worth of surface to run against.

Column state model (blocked/ready/building/merging/done)

Define the five ticket states and the moves between them in code, not just in prose: a TicketState type with the five values, and the transition rules that say which moves are automatic and which are manual.

A red check in merging sends a ticket back to building automatically — the merge loop does this (#st-build-run), a person never drags a ticket out of merging by hand. A red held-out step does not move a ticket at all: it is not a per-ticket failure, it is a state of the whole run (#st-g2-heldout), so it surfaces as the board's header badge and a new ticket filed into ready, not as some existing ticket changing column.

The model intentionally has no "cancelled" or "failed" terminal state. A ticket that fails its checks in building just stays in building, with a retry count, until either it passes or a person archives it by hand. There is no board state for "we tried and gave up" — that is a human decision, made through the archive action, not something the model infers from a retry count crossing some threshold.

Tests cover every legal transition in the table (blocked→ready, ready→building, building→ready, building→merging, merging→building, merging→done) and assert that every other pair throws if some future caller tries to force it — the board's drag logic leans on that same table so the UI and the model can never disagree about what is allowed.
