## What to build

When a builder starts on a ticket, a step author agent with no tools writes Given, When, Then steps from the same brief; the program stores them in werk's store, out of the builder's worktree. A follow-up ticket gets no step author.

A held-out run starts the binder in a temporary worktree of the main line. The binder maps each step to a browser test in its own folder, never changes step text, records a failure and stops, and fixes only its own errors. If it changes a file outside its folder, the whole report is void. Each step ends green, red, or not run when the binder failed, timed out or could not bind it; the binder's time limit grows with the number of steps. Not-run files nothing. A binder error is retried once at the end of the run and then waits for a person.

The product's browser test run looks for tests in its own spec folder and in the binder's folder, so a held-out test runs on the same server, fake agent and fixture project as a product spec.

A red step reaches the builder of that ticket as the step text only. The gate verb keeps G2 waiting while any held-out step is not green on the main line.

## Acceptance criteria

- [ ] The step author's launch record has no tools, and its steps are not inside the builder's worktree.
- [ ] A test placed in the binder's folder runs under `make e2e` with the product specs.
- [ ] A binder that edits a product file voids its report.
- [ ] A binder timeout gives not run, files nothing, and G2 stays waiting.
- [ ] A red step keeps G2 waiting, and the next builder prompt holds that step's text and no test code.
