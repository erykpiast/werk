## What to build

After a merge, a user path that must work does not work on the merged product. Make it work. Each path, word for word:

Scenario: A card with a missing fact cannot become decided, and the printed command fixes it
Given a map with a card that has a decider, a depends_on basis, and weighed options, but no kill criteria
When the agent sets the card to decided
Then the command fails with a non-zero exit
And the output names the missing kill criteria and prints one command that adds it
And the card still shows its earlier status on the map
And the log has no new status event for the card
When the agent runs the printed command with a kill criterion filled in
And the agent sets the card to decided again
Then the command succeeds
And the card shows as decided on the map

Scenario: Each missing fact prints its own fixing command
Given a map with four cards that have all the required facts except one each
And the first card has no decider, the second has no depends_on basis and no stated lack of one, the third has no weighed options and no unchallenged flag, and the fourth has no kill criteria
When the agent sets each card to decided in turn
Then each attempt fails and appends no event
And each failure prints a different command, and that command supplies the fact that card is missing
When the agent runs each printed command and sets each card to decided again
Then all four cards show as decided

Scenario: A stated lack of basis and an unchallenged flag satisfy the check
Given a map with a card that has a decider and kill criteria but no depends_on edges and no weighed options
When the agent records on the card that it has no basis, with a reason
And the agent records the card as unchallenged
And the agent sets the card to decided
Then the command succeeds
And the card shows as decided on the map with the stated reason and the unchallenged flag visible

Scenario: An amend of a decided card cannot remove a required fact
Given a map with a card that passed the check and shows as decided
When the agent amends the card to remove its kill criteria
Then the command fails with a non-zero exit
And the output prints the command that supplies the kill criteria
And the log has no new amend event for the card
And the card on the map still shows its kill criteria and its decided status
When the agent amends the card to change only its body text and keeps all facts
Then the amend succeeds and the map shows the new text

Scenario: Adding a card and setting it open are not checked
Given an empty map
When the agent adds a card with only a title and a body, with no decider, no basis, no options, and no kill criteria
Then the command succeeds and the card shows on the map
When the agent sets the card to open
Then the command succeeds and the card shows as open
But when the agent sets the card to decided
Then the command fails and the card stays open

Scenario: A reopen without a reason is refused and leaves the map unchanged
Given a map where card "Pricing" is decided and card "Checkout" depends on "Pricing"
When the person reopens "Pricing" and gives no reason
Then the reopen is refused with a message that a reason of postponed or rejected is required
And "Pricing" is still shown as decided
And the staleness listing shows no marked cards

Scenario: A rejected reopen marks only the next hop as stale, and a review moves the mark one hop on
Given a map where card "Storage" is decided, card "API" depends on "Storage", and card "Client" depends on "API"
And card "Storage" has a child card "Schema"
When the person reopens "Storage" with the reason rejected
Then the staleness listing shows "API" and "Schema" as stale, each with the reason rejected and a trace that names the reopen of "Storage" and the link it followed
And the listing shows no mark on "Client"
And the browser draws "API" and "Schema" in red with the reason rejected on the card
When the person reviews "API" and amends it
Then "API" no longer shows as stale
And "Schema" still shows as stale
And "Client" now shows as stale, with a trace that names the change to "API"

Scenario: A postponed reopen marks every downstream card as paused in grey and keeps its status colour
Given a map where card "Engine" is decided, "Parser" depends on "Engine", "Renderer" depends on "Parser", and "Export" depends on "Renderer"
And "Parser" is decided and "Renderer" is open
When the person reopens "Engine" with the reason postponed
Then the staleness listing shows "Parser", "Renderer" and "Export" as paused, each with the reason postponed and a trace back to the reopen of "Engine"
And no card shows as stale
And the browser draws "Parser", "Renderer" and "Export" with a grey paused mark
And "Parser" still shows the decided status colour and "Renderer" still shows the open status colour
When the person resumes the work on "Engine"
Then no card shows a paused mark in the staleness listing or in the browser

Scenario: Stale wins when a postponement and an invalidation reach the same card
Given a map where card "Billing" depends on decided card "Auth" and on decided card "Ledger"
And card "Report" depends on "Billing"
When the person reopens "Auth" with the reason postponed
And the person reopens "Ledger" with the reason rejected
Then the staleness listing shows "Billing" as stale with the reason rejected and a trace that names the reopen of "Ledger"
And the browser draws "Billing" in red, not grey
And "Report" shows as paused with the reason postponed

Scenario: Clearing one stale mark leaves the other marks in place
Given a map where cards "Search" and "Filters" both depend on decided card "Index"
And the person reopened "Index" with the reason rejected, so "Search" and "Filters" show as stale
When the person reviews "Search" and confirms it unchanged
Then "Search" no longer shows as stale in the staleness listing or in the browser
And "Filters" still shows as stale with the reason rejected and its trace to the reopen of "Index"
