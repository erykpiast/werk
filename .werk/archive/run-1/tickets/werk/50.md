## What to build

`werk plan <root>` plans one decided subtree. Its first event in the run record is the tier: feature. No tier is parsed from prose, and no tier is raised during a run, so every gate waits for the person.

The plan starts the spec writer as a headless agent over the subtree, the cards it links one hop out, and the map index. Then it starts the ticket writer over the spec. Each writer also writes a list of answer records: a slug, a title, a why, and a body. The answer proposer proposes each record as a ghost that refines the subtree root, with the id made of the root id, a hyphen, and the slug, and the agent as the one who decides. A record it cannot propose, such as an id already in the map, is reported, and the plan exits non-zero.

The plan runs the ticket checks on the new set. Each ticket that passes goes to the board as ready, or blocked when it has unmet blockers. A failed set check blocks only the tickets it names. A plan over a subtree that already has open tickets extends them. An open ticket that the current spec no longer needs is archived with that reason, and a restore puts it back.

## Acceptance criteria

- [ ] The first event of the run record is a tier event with the value feature, and no plan path writes another tier.
- [ ] With fake writers, the plan writes the spec and the ticket files, and each ticket is on the board as ready or blocked.
- [ ] Two answer records become two ghosts under the subtree root with ids root-slug, and the agent is their who.
- [ ] A record whose id is already in the map is printed, and the plan exits non-zero.
- [ ] A fake ticket writer that leaves one ticket without its touches line blocks that ticket with the failure, and the other tickets stay ready.
- [ ] An open ticket that the new ticket set does not keep is archived with the reason, and a restore brings it back to its column.
