## What to build

After a merge, a user path that must work does not work on the merged product. Make it work. Each path, word for word:

Scenario: A second plan of the same subtree extends the spec and continues the ticket numbers
Given a person has planned a subtree once, and the board shows its one spec and tickets 1 to 3 as ready
And ticket 1 is building and ticket 2 is done
When the person adds a new decided card under that subtree and plans the same subtree again
Then the board still shows one spec for the subtree, and the spec text now covers the new card
And ticket 3 keeps its number and shows the rewritten text
And a new ticket appears with number 4, and no ticket number repeats
And ticket 1 still shows building and ticket 2 still shows done, with their text unchanged

## Before you build (#st-heldout-unbuilt-close)

Check two facts for each path. First, the path needs a capability that the main line does not provide and that another ticket, one that is not merged yet, builds. A capability is an operation of the command line, a screen or route, a field or kind of event in the log, or a behaviour of an agent. Second, the seam behind the path has unit tests that state its outcome, and they pass on the main line. When both facts hold for every path, change no code: the paths are not run until that ticket merges. When the second fact fails for a path, write the missing unit test at the seam and change nothing else for that path.

## Acceptance criteria

- [ ] A user can follow "A second plan of the same subtree extends the spec and continues the ticket numbers" from start to end, or both facts above hold for it and a passing unit test at its seam states its outcome
